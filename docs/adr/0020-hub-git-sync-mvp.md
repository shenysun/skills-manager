# ADR-0020: Hub git-ification for multi-machine sync (MVP)

Two competitors attack from both flanks: xingkongliang ships full multi-device sync (device codes, OS-keychain tokens, skill-level merge, snapshots) and skl sells exact cross-machine rebuilds. We need multi-machine sync, but not their machinery: git already is a merge tool, and wrapping it in device codes and per-skill conflict UIs would fight both our CLI-first posture and the single-writer hub model.

**Decision:** the hub itself becomes a git repository; push/pull over any remote the user chooses is the sync mechanism. An explicit `sync` command group, each command thin: `sync init [--remote <url>]` (git init, canonical `.gitignore`, baseline commit when the tree has anything to commit — modifications included, a baseline that left dirt behind would defeat pull's clean-tree precondition — optional remote attach, **adopt** semantics: an existing `.git/` is the user being a step ahead, not an error; history kept, only missing `.gitignore` lines appended, and the adopt output lists exactly what it backfilled — zero omission), `sync push` (snapshot commit at push time — `skills/`, `collections/`, `registry.yaml` tracked; `.backups/` and `.skills/` are machine-local and ignored; no write-point instrumentation, no auto-commit), `sync pull` (requires a clean tree — dirty means nonzero exit plus guidance, never stash on the user's behalf; fetch + merge, merge commits allowed; conflicts pass git's nonzero exit through with a `git -C <hub>` resolution pointer — **no built-in merge decisions, ever**), and `sync status` (read-only, zero-network: git-managed?, remote configured?, dirty count, ahead/behind against remote-tracking refs annotated as last-fetch, last sync commit; `--json`). Boundary behaviors: push without a remote or without git identity exits nonzero with guidance; push with nothing to commit and an up-to-date branch reports "already in sync" and exits 0. Pull ends with a report-only line noting that newly pulled skills are not yet distributed (the user distributes per machine). No size gate (GitHub's 100 MB hard limit backstops); `sync init` output carries a one-line reminder that the hub is about to be pushed to a remote — confirm it holds no secrets.

This ADR amends ADR-0012's non-goal wording "the CLI keeps no network capability beyond git clone and catalog refresh" to "**beyond git transport (clone/fetch/push/pull) and catalog refresh**". Bootstrap does **not** git-init the hub (ADR-0014 unchanged — sync is the user's explicit opt-in). `doctor` and `skills-manager status` gain nothing in v1; `sync status` is the only visibility surface. Deferred: dashboard integration, any remote/auth management (credentials stay with the user's git), size gates, and pre-push secret scanning (a separate roadmap item).

_Avoid_: device codes, OS-keychain tokens, or any skills-manager-managed sync auth; skill-level merge or conflict-resolution UI (keep-mine/use-remote/keep-both is the desktop rival's lane); auto-commit at write points; stashing or rebasing on the user's behalf; committing `.backups/` or the distribution index (`.skills/`) — distribution is per-machine; implicit git init at bootstrap; doctor/status resident reminders for a dirty sync tree.
